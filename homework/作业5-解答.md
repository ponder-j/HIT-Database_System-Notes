# 数据库并发控制问题解析

## 第1题：调度可串行化判断

### 问题描述
- $r_i(X)$ 与 $w_i(X)$ 分别表示事物T读、写数据项单元X
- 一个并发调度可以抽象为读、写中
- 判断两个调度是否可串行化

### 调度S和S'
**调度S：**
```
r₂(A); r₁(B); w₂(A); r₃(A); w₁(B); w₃(A); r₂(B); w₂(B)
```

**调度S'：**
```
r₂(A); r₁(B); w₂(A); r₂(B); r₃(A); w₁(B); w₃(A); w₂(B)
```

### 解答思路

#### 1. 构造冲突关系图

对于调度S，分析冲突操作（涉及同一数据项且至少有一个写操作）：

**对数据项A的冲突：**
- r₂(A) → w₂(A)：T₂内部顺序
- w₂(A) → r₃(A)：T₂写后T₃读（WR冲突），T₂ → T₃
- r₃(A) → w₃(A)：T₃内部顺序

**对数据项B的冲突：**
- r₁(B) → w₁(B)：T₁内部顺序
- w₁(B) → r₂(B)：T₁写后T₂读（WR冲突），T₁ → T₂
- r₂(B) → w₂(B)：T₂内部顺序

**调度S的优先图：**
```
T₁ → T₂ → T₃
```

这是一个**无环图**，因此调度S是**冲突可串行化**的，等价于串行调度 T₁ → T₂ → T₃。

---

对于调度S'，分析冲突操作：

**对数据项A的冲突：**
- r₂(A) → w₂(A)：T₂内部顺序
- w₂(A) → r₃(A)：T₂写后T₃读，T₂ → T₃
- r₃(A) → w₃(A)：T₃内部顺序

**对数据项B的冲突：**
- r₁(B) → w₁(B)：T₁内部顺序
- r₂(B) → w₂(B)：T₂内部顺序
- w₁(B) → w₂(B)：T₁写后T₂写（WW冲突），T₁ → T₂

**调度S'的优先图：**
```
T₁ → T₂ → T₃
```

这也是一个**无环图**，因此调度S'也是**冲突可串行化**的，等价于串行调度 T₁ → T₂ → T₃。

### 结论
两个调度都是可串行化的，因为它们的冲突优先图都不含环，且都等价于相同的串行调度 T₁ → T₂ → T₃。

## 第2题：两阶段锁协议(2PL)

### 问题描述
```
T1:
read(A);
read(B);
if A > B then B := A;

T2:
read(B);
read(A);
if B < 0 then A := B * B;
```

### (1) 简述两段锁协议（2PL）并添加加锁和解锁指令

#### 两阶段锁协议(2PL)定义
两阶段锁协议要求每个事务的执行分为两个阶段：
1. **增长阶段（Growing Phase）**：事务可以获得锁，但不能释放锁
2. **收缩阶段（Shrinking Phase）**：事务可以释放锁，但不能获得新锁

#### 添加锁指令后的事务

**T1（遵守2PL）：**
```
lock(A);
read(A);
lock(B);
read(B);
if A > B then 
    write(B);
unlock(A);
unlock(B);
```

**T2（遵守2PL）：**
```
lock(B);
read(B);
lock(A);
read(A);
if B < 0 then 
    write(A);
unlock(B);
unlock(A);
```

---

### (2) 2PL下T1和T2的一个正确调度

一个符合2PL协议的正确调度示例：

```
T1: lock(A);
T1: read(A);
T1: lock(B);
T1: read(B);
T1: if A > B then write(B);
T1: unlock(A);
T1: unlock(B);
T2: lock(B);
T2: read(B);
T2: lock(A);
T2: read(A);
T2: if B < 0 then write(A);
T2: unlock(B);
T2: unlock(A);
```

这是一个串行调度（T1完全执行完后再执行T2），满足2PL协议且不会产生冲突。

---

### (3) T1和T2可能发生的死锁及调度

#### 死锁场景

**会导致死锁的调度：**
```
T1: lock(A);
T1: read(A);
T2: lock(B);
T2: read(B);
T1: wait for lock(B);  // T1等待T2释放B
T2: wait for lock(A);  // T2等待T1释放A
// 死锁发生！
```

#### 死锁原因分析
- T1持有A的锁，等待B的锁
- T2持有B的锁，等待A的锁
- 形成循环等待：T1 → T2 → T1

#### 死锁发生的完整调度
```
T1: lock(A);
T1: read(A);
T2: lock(B);
T2: read(B);
T1: request lock(B); // 被T2阻塞
T2: request lock(A); // 被T1阻塞
// 死锁！
```

---

### (4) 数据库实际应用中常见的死锁检测方法

#### 常见死锁检测方法

**1. 等待图法（Wait-For Graph）**
- 构造等待图：节点表示事务，边 Ti → Tj 表示Ti等待Tj持有的资源
- 周期性检测图中是否存在环
- 如果存在环，则说明发生了死锁
- 选择一个或多个事务回滚以打破环

**2. 超时法（Timeout）**
- 为每个事务设置等待超时时间
- 如果事务等待时间超过阈值，认为可能发生死锁
- 回滚该事务并重新执行
- 优点：实现简单，无需维护等待图
- 缺点：可能误判，不够精确

**3. 死锁预防**
- **资源有序分配**：规定所有事务必须按相同顺序申请锁（如按数据项字母顺序）
- **一次性加锁**：事务开始前一次性申请所有需要的锁
- **优先级方法**：
  - Wait-Die：老事务等待年轻事务，年轻事务遇到老事务则回滚
  - Wound-Wait：老事务抢占年轻事务，年轻事务等待老事务

**4. 死锁避免**
- 在授予锁之前检查是否会导致死锁
- 使用银行家算法等策略
- 只在确保安全的情况下授予锁

#### 实际数据库系统的做法

主流数据库系统通常采用**等待图法 + 超时法**的组合：
- MySQL InnoDB：使用等待图检测死锁，周期性检测
- PostgreSQL：使用超时机制检测死锁
- Oracle：使用等待图法，每10秒检测一次
- SQL Server：使用死锁检测线程，维护锁资源图

发现死锁后，系统会选择代价最小的事务作为牺牲者（victim）进行回滚。

---

## 总结

1. **可串行化判断**：使用冲突优先图，无环则可串行化
2. **2PL协议**：分为增长和收缩两个阶段，保证可串行化但可能导致死锁
3. **死锁**：循环等待导致，需要检测和处理机制
4. **死锁检测**：等待图法、超时法、预防和避免等多种策略结合使用
