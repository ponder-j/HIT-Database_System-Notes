# 数据库并发控制问题解析

## 第1题：调度可串行化判断

### 问题描述
- $r_i(X)$ 与 $w_i(X)$ 分别表示事物T读、写数据项单元X
- 一个并发调度可以抽象为读、写中
- 判断两个调度是否可串行化

### 调度S和S'
**调度S：**
```
r₂(A); r₁(B); w₂(A); r₃(A); w₁(B); w₃(A); r₂(B); w₂(B)
```

**调度S'：**
```
r₂(A); r₁(B); w₂(A); r₂(B); r₃(A); w₁(B); w₃(A); w₂(B)
```

### 解答思路

#### 1. 构造冲突关系图

对于调度S，分析冲突操作（涉及同一数据项且至少有一个写操作）：

**对数据项A的冲突：**
- r₂(A) → w₂(A)：T₂内部顺序
- w₂(A) → r₃(A)：T₂写后T₃读（WR冲突），T₂ → T₃
- r₃(A) → w₃(A)：T₃内部顺序

**对数据项B的冲突：**
- r₁(B) → w₁(B)：T₁内部顺序
- w₁(B) → r₂(B)：T₁写后T₂读（WR冲突），T₁ → T₂
- r₂(B) → w₂(B)：T₂内部顺序

**调度S的优先图：**
```
T₁ → T₂ → T₃
```

这是一个**无环图**，因此调度S是**冲突可串行化**的，等价于串行调度 T₁ → T₂ → T₃。

---

对于调度S'，分析冲突操作：

**对数据项A的冲突：**
- r₂(A) → w₂(A)：T₂内部顺序
- w₂(A) → r₃(A)：T₂写后T₃读，T₂ → T₃
- r₃(A) → w₃(A)：T₃内部顺序

**对数据项B的冲突：**
- r₁(B) → w₁(B)：T₁内部顺序
- r₂(B) → w₂(B)：T₂内部顺序
- w₁(B) → w₂(B)：T₁写后T₂写（WW冲突），T₁ → T₂

**调度S'的优先图：**
```
T₁ → T₂ → T₃
```

这也是一个**无环图**，因此调度S'也是**冲突可串行化**的，等价于串行调度 T₁ → T₂ → T₃。

### 结论
两个调度都是可串行化的，因为它们的冲突优先图都不含环，且都等价于相同的串行调度 T₁ → T₂ → T₃。

## 第2题：两阶段锁协议(2PL)

### 问题描述
```
T1:
read(A);
read(B);
if A > B then B := A;

T2:
read(B);
read(A);
if B < 0 then A := B * B;
```

### (1) 简述两段锁协议（2PL）并添加加锁和解锁指令

#### 两阶段锁协议(2PL)定义
两阶段锁协议要求每个事务的执行分为两个阶段：
1. **增长阶段（Growing Phase）**：事务可以获得锁，但不能释放锁
2. **收缩阶段（Shrinking Phase）**：事务可以释放锁，但不能获得新锁

#### 添加锁指令后的事务

**T1（遵守2PL）：**
```
lock(A);
read(A);
lock(B);
read(B);
if A > B then 
    write(B);
unlock(A);
unlock(B);
```

**T2（遵守2PL）：**
```
lock(B);
read(B);
lock(A);
read(A);
if B < 0 then 
    write(A);
unlock(B);
unlock(A);
```

---

### (2) 2PL下T1和T2的一个正确调度

一个符合2PL协议的正确调度示例：

```
T1: lock(A);
T1: read(A);
T1: lock(B);
T1: read(B);
T1: if A > B then write(B);
T1: unlock(A);
T1: unlock(B);
T2: lock(B);
T2: read(B);
T2: lock(A);
T2: read(A);
T2: if B < 0 then write(A);
T2: unlock(B);
T2: unlock(A);
```

这是一个串行调度（T1完全执行完后再执行T2），满足2PL协议且不会产生冲突。

---

### (3) T1和T2可能发生的死锁及调度

#### 死锁场景

**会导致死锁的调度：**
```
T1: lock(A);
T1: read(A);
T2: lock(B);
T2: read(B);
T1: wait for lock(B);  // T1等待T2释放B
T2: wait for lock(A);  // T2等待T1释放A
// 死锁发生！
```

#### 死锁原因分析
- T1持有A的锁，等待B的锁
- T2持有B的锁，等待A的锁
- 形成循环等待：T1 → T2 → T1

#### 死锁发生的完整调度
```
T1: lock(A);
T1: read(A);
T2: lock(B);
T2: read(B);
T1: request lock(B); // 被T2阻塞
T2: request lock(A); // 被T1阻塞
// 死锁！
```

---

### (4) 数据库实际应用中常见的死锁检测方法

#### 常见死锁检测方法

**1. 等待图法（Wait-For Graph）**
- 构造等待图：节点表示事务，边 Ti → Tj 表示Ti等待Tj持有的资源
- 周期性检测图中是否存在环
- 如果存在环，则说明发生了死锁
- 选择一个或多个事务回滚以打破环

**2. 超时法（Timeout）**
- 为每个事务设置等待超时时间
- 如果事务等待时间超过阈值，认为可能发生死锁
- 回滚该事务并重新执行
- 优点：实现简单，无需维护等待图
- 缺点：可能误判，不够精确

**3. 死锁预防**
- **资源有序分配**：规定所有事务必须按相同顺序申请锁（如按数据项字母顺序）
- **一次性加锁**：事务开始前一次性申请所有需要的锁
- **优先级方法**：
  - Wait-Die：老事务等待年轻事务，年轻事务遇到老事务则回滚
  - Wound-Wait：老事务抢占年轻事务，年轻事务等待老事务

**4. 死锁避免**
- 在授予锁之前检查是否会导致死锁
- 使用银行家算法等策略
- 只在确保安全的情况下授予锁

#### 实际数据库系统的做法

主流数据库系统通常采用**等待图法 + 超时法**的组合：
- MySQL InnoDB：使用等待图检测死锁，周期性检测
- PostgreSQL：使用超时机制检测死锁
- Oracle：使用等待图法，每10秒检测一次
- SQL Server：使用死锁检测线程，维护锁资源图

发现死锁后，系统会选择代价最小的事务作为牺牲者（victim）进行回滚。

## 第3题：WAL日志与故障恢复

### 问题描述
已知数据库采用即时更新方法（undo-redo方法）记录WAL日志。设故障发生时WAL日志文件内容如下：

```
<T1, begin>
<T1, A, 114, 114514>
<T2, begin>
<T1, B, "bit", "bites">
<T1, commit>
<T3, begin>
<T3, B, "bites", "bitesdb">
<T2, A, 114514, 1919810>
```

当系统重启后，DBMS基于该WAL日志文件进行故障恢复。

### 3.1 数据库系统的日志恢复策略类型

#### 恢复策略分类

**Undo/Redo型（即时更新）：**
- **特点**：事务在提交前就可以将修改写入磁盘
- **日志记录**：同时记录修改前的值（old value）和修改后的值（new value）
- **恢复时**：
  - 对已提交的事务执行 **Redo**（重做）
  - 对未提交的事务执行 **Undo**（撤销）

**Steal? No Steal + Force? No Force?**

这两个概念描述了缓冲区管理策略：

1. **Steal vs No-Steal（窃取策略）**
   - **Steal**：允许未提交事务的脏页面写入磁盘
   - **No-Steal**：不允许未提交事务的脏页面写入磁盘
   
2. **Force vs No-Force（强制策略）**
   - **Force**：事务提交时必须将所有修改的页面写入磁盘
   - **No-Force**：事务提交时不强制将所有修改写入磁盘

#### 该数据库系统的策略

该系统采用 **Undo/Redo** 型恢复策略，对应的缓冲区管理策略是：

- **Steal**：允许未提交事务的修改写入磁盘（需要Undo能力）
- **No-Force**：提交时不强制写入所有页面（需要Redo能力）

这是最灵活的策略，性能最好，但恢复时需要同时支持Undo和Redo操作。

**每一项的具体内容：**

| 策略 | 含义 | 对应操作 |
|------|------|----------|
| Steal | 未提交事务的脏页可写入磁盘 | 需要Undo |
| No-Steal | 未提交事务的脏页不可写入磁盘 | 不需要Undo |
| Force | 提交时强制写入所有修改 | 不需要Redo |
| No-Force | 提交时不强制写入所有修改 | 需要Redo |

---

### 3.2 进行故障恢复时需要Undo和Redo的事务

#### 分析日志内容

从WAL日志中分析各事务状态：

**T1事务：**
```
<T1, begin>
<T1, A, 114, 114514>
<T1, B, "bit", "bites">
<T1, commit>  ✓ 已提交
```

**T2事务：**
```
<T2, begin>
<T2, A, 114514, 1919810>
（无commit记录）  ✗ 未提交
```

**T3事务：**
```
<T3, begin>
<T3, B, "bites", "bitesdb">
（无commit记录）  ✗ 未提交
```

#### 恢复操作分配

**需要进行 Redo 的事务：**
- **T1**（已提交）
  - Redo: A = 114514
  - Redo: B = "bites"

**需要进行 Undo 的事务：**
- **T2**（未提交）
  - Undo: A = 114514（恢复为114514）
- **T3**（未提交）
  - Undo: B = "bitesdb"（恢复为"bites"）

#### 具体理由

1. **T1需要Redo**：因为T1已经提交，但由于采用No-Force策略，其修改可能还未完全写入磁盘，需要重做以确保持久性
2. **T2需要Undo**：T2未提交就发生故障，其修改可能已写入磁盘（Steal策略），需要撤销以保证原子性
3. **T3需要Undo**：同T2，未提交事务需要撤销

#### 恢复过程

**初始状态（故障前磁盘可能的状态）：**
- 不确定，取决于哪些脏页被写入

```
2. Undo阶段（撤销未提交事务，从后往前）：
   T2: A: 1919810 → 114514

3. Redo阶段（重做已提交事务，从前往后）：
   T1: A: 114 → 114514
```

## 第4题：STEAL和NO-FORCE缓冲管理策略下的WAL日志分析

### 问题描述

DBMS采用STEAL和NO-FORCE缓冲策略。假设当DBMS执行检查点时会将数据缓冲区中所有的脏数据块写入相应的数据文件，保证数据库的一致性。

下面是数据库发生故障后的一份WAL日志，Ti表示事务Ti，数据项X，更新前数据项的值A，更新后数据项的值B。

**WAL日志内容：**

| LSN | WAL Record |
|-----|------------|
| 1 | <T1, BEGIN> |
| 2 | <T1, X, 1, 2> |
| 3 | <T2, BEGIN> |

| 5 | <T1, COMMIT> |
| 6 | <T2, Y, 2, 3> |
| 7 | <T3, BEGIN> |

### 4.1 恢复数据XYZ时数据库磁盘文件上的值

#### 分析CHECKPOINT时刻的状态

在LSN=10时发生了CHECKPOINT，此时：
- CHECKPOINT会将所有脏页刷新到磁盘
- 需要确定CHECKPOINT前哪些修改已经在内存中

**CHECKPOINT前的事务操作：**

1. **T1（已提交）：**
   - LSN 2: X: 1 → 2
   - LSN 5: COMMIT
   - 结论：T1的修改会在CHECKPOINT时写入磁盘

2. **T2（未提交）：**
   - LSN 4: Y: 2 → 3
   - LSN 6: Y: 2 → 3（重复操作，实际可能是Y已经是3了）
   - LSN 9: X: 2 → 4
   - 结论：这些修改在CHECKPOINT时也会写入磁盘（STEAL策略）

3. **T3（未提交）：**
   - LSN 8: Z: 1 → 2
   - 结论：这个修改在CHECKPOINT时也会写入磁盘

**CHECKPOINT时磁盘上的值：**
- **X = 4**（T1的修改2，然后T2的修改4）
- **Y = 3**（T2的修改3）
- **Z = 2**（T3的修改2）

#### 最终答案

在DBMS需要进行恢复数据的时候，数据库磁盘文件上数据项XYZ的值分别是：
- **X = 4**
- **Y = 3**  
- **Z = 2**

### 4.2 对WAL日志进行故障恢复时事务T1、T2、T3的处理

#### 分析各事务状态

**从日志中确定事务最终状态：**

1. **T1：**
   - LSN 5: `<T1, COMMIT>` ✓
   - 状态：已提交

2. **T2：**
   - 无COMMIT或ABORT记录 ✗
   - 状态：未提交（活跃事务）

3. **T3：**
   - LSN 13: `<T3, COMMIT>` ✓
   - 状态：已提交

#### 恢复处理策略

**根据Undo/Redo恢复算法：**

**T1的处理：**
- 已在CHECKPOINT前提交
- 其修改已经通过CHECKPOINT写入磁盘
- **不需要Redo**（因为CHECKPOINT已保证写入）
- 不需要Undo

**T2的处理：**
- 未提交的活跃事务
- 需要 **Undo**（撤销所有修改）
- 从日志末尾向前扫描，撤销T2的所有操作：
  - Undo LSN 14: Z: 4 → 3
  - Undo LSN 11: Y: 4 → 3  
  - Undo LSN 9: X: 4 → 2
  - Undo LSN 6: Y: 3 → 2
  - Undo LSN 4: Y: 3 → 2

**T3的处理：**
- 在CHECKPOINT后提交（LSN 13）
- CHECKPOINT到COMMIT之间的修改需要 **Redo**：
  - Redo LSN 12: Z: 2 → 3
- 原因：虽然T3提交了，但其修改可能还在缓冲区中未写入磁盘（NO-FORCE策略）

#### 总结

| 事务 | 状态 | 处理方式 | 原因 |
|------|------|----------|------|
| T1 | 已提交 | 无需操作 | CHECKPOINT前提交，修改已持久化 |
| T2 | 未提交 | **Undo** | 未提交事务，需撤销所有修改 |
| T3 | 已提交 | **Redo** | CHECKPOINT后提交，需重做以保证持久性 |

#### 恢复执行过程

**Step 1: 磁盘初始状态（故障时）**
- X = 4
- Y = 3
- Z = 2

**Step 2: 执行Undo操作（撤销T2）**

- LSN 11: Y从3改为4，但磁盘上Y=3，所以不用撤销
- LSN 14: Z从3改为4，但磁盘上Z=2，需要确认

让我重新分析磁盘状态和Undo过程：

**更正：磁盘状态在CHECKPOINT时**
根据CHECKPOINT的定义，它刷新所有脏页：
- T1: X = 2（LSN 2）

**Redo T3（从前往后）：**

故障恢复完成后：
- **X = 2**
- **Y = 2**
- **Z = 3**

#### 详细过程说明

```

Undo T2:
  撤销 LSN 9: X = 4 → 2
  撤销 LSN 4,6: Y = 3 → 2
  
Redo T3:
  重做 LSN 12: Z = 2 → 3
```

- 在检查点后开始，在故障时仍在运行（未提交）
- 状态：未提交
- **操作：需要Undo（撤销）**
- 原因：未提交的活跃事务

#### 总结表

| 事务 | 与检查点关系 | 与故障点关系 | 恢复操作 |
|------|-------------|-------------|----------|
| T₁ | 提交在检查点前 | 早已完成 | **不需要操作** |
| T₂ | 开始在检查点前 | 提交在故障前 | **需要Redo** |
| T₃ | 开始在检查点前 | 故障时未提交 | **需要Undo** |
| T₄ | 开始在检查点后 | 提交在故障前 | **需要Redo** |
| T₅ | 开始在检查点后 | 故障时未提交 | **需要Undo** |

#### 问题分析

数据库系统发生故障时，需要给出恢复系统需要undo的事务列表和需要redo的事务列表。

**分析各事务状态：**

**T₆：**
- `<T₆, begin>` 在checkpoint前
- `<T₆, commit>` 在checkpoint后
- 状态：已提交
- **操作：需要Redo**

**T₇：**
- `<T₇, begin>` 在checkpoint前
- 无commit记录

- **操作：需要Undo**

**T₈：**
- `<T₈, begin>` 在checkpoint前
- 无commit记录
- 状态：未提交
- **操作：需要Undo**

**需要Undo的事务列表：** T₇, T₈

### 5.3 基于检查点的故障恢复过程（T₆-T₈）

#### 恢复过程详细步骤

**Phase 1: 分析阶段（Analysis）**

从checkpoint开始向前扫描日志：
1. 识别checkpoint时的活跃事务
2. 确定哪些事务已提交，哪些未提交

**分析结果：**
- Checkpoint时活跃事务：T₆, T₇, T₈
- 已提交事务：T₆
- 未提交事务：T₇, T₈

**Phase 2: Redo阶段（从checkpoint开始向前）**

重做所有已提交事务在checkpoint后的操作：

```
Redo T₆:
  （T₆在checkpoint前的操作已经持久化）
  无checkpoint后的操作需要redo
```

注意：T₆的commit在checkpoint后，但它的数据修改`<T₆, X, 100, 1>`在checkpoint前，checkpoint已经将这个修改刷新到磁盘了。

**Phase 3: Undo阶段（从日志末尾向前）**

撤销所有未提交事务的操作：

```
Undo T₈（从后往前）:
  撤销 <T₈, Z, 9, 10>: Z = 10 → 9
  撤销 <T₈, Z, 10, 9>: Z = 9 → 10
  撤销 <T₈, Y, 6, 8>: Y = 8 → 6

Undo T₇（从后往前）:
  撤销 <T₇, Y, 50, 6>: Y = 6 → 50
  撤销 <T₇, X, 1, 3>: X = 3 → 1
```

#### 恢复后的数据状态

假设初始状态为：
- X = 100
- Y = 50  
- Z = 10

**执行恢复后：**

1. **T₆的修改保留**（已提交）：
   - X: 100 → 1

2. **T₇的修改撤销**（未提交）：
   - X: 1 → 1（T₇的修改3被撤销）
   - Y: 50（T₇的修改被撤销）

3. **T₈的修改撤销**（未提交）：
   - Y: 50（T₈的修改被撤销）
   - Z: 10（T₈的修改被撤销）

**最终结果：**
- **X = 1**（T₆的修改）
- **Y = 50**（恢复到初始值）
- **Z = 10**（恢复到初始值）

#### 完整恢复过程图示

```
时间线：
────────[checkpoint]────────[crash]────→
   T₆: X=100→1              commit
   T₇: X=1→3, Y=50→6        (未提交)
   T₈: Y=6→8, Z=10→9→10     (未提交)

恢复过程：
1. 分析：识别T₆已提交，T₇、T₈未提交
2. Redo：T₆已在checkpoint前完成，无需redo
3. Undo：
   - T₈: Z恢复10, Y恢复6
   - T₇: Y恢复50, X恢复1
   
注意：由于T₆的X=1修改在checkpoint前，
     checkpoint已确保写入磁盘，所以X=1保留

最终：X=1, Y=50, Z=10
```

## 总结

1. **可串行化判断**：使用冲突优先图，无环则可串行化
2. **2PL协议**：分为增长和收缩两个阶段，保证可串行化但可能导致死锁
3. **死锁**：循环等待导致，需要检测和处理机制
4. **死锁检测**：等待图法、超时法、预防和避免等多种策略结合使用
5. **WAL日志恢复**：基于Undo/Redo机制，已提交事务需要Redo，未提交事务需要Undo
6. **STEAL/NO-FORCE策略**：最灵活但恢复最复杂，需要同时支持Undo和Redo
7. **检查点恢复**：利用检查点减少恢复时需要扫描的日志量，提高恢复效率
